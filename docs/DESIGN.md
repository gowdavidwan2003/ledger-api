# Design notes

This document covers why the ledger is built the way it is, the alternatives I considered, and what changes at scale.

## 1. Concurrency: pessimistic row lock

**Problem.** Two debits of ₹60 arrive together for an account holding ₹100. Without coordination, both read `100`, both pass the check, and both write. The result is a balance of −₹20, or ₹40 with one debit lost.

**Choice.** One DB transaction per posting, starting with `SELECT … FOR UPDATE` on the account row. The second request blocks on the lock until the first commits, then reads the new balance.

**Alternatives considered:**

| Option | Why not |
|---|---|
| Single statement: `UPDATE accounts SET balance = balance - $1 WHERE id = $2 AND balance >= $1` | Atomic and fast, but idempotency and `balance_after` then need more round trips or a CTE. Readability suffers, and the rules move into SQL. A good choice for a hot path, though. |
| `SERIALIZABLE` isolation | Correct, but conflicting transactions abort with `40001` and the app must retry them. That means more code and wasted work under contention. |
| Optimistic locking (`version` column) | Same retry problem. It suits low-contention data; a single account's balance is high-contention by nature. |
| Application-level locks (Python `threading.Lock`, Redis) | Breaks with multiple processes or servers. The database already is the single source of truth. |

**Scope of the lock.** Only that account's row is locked. Other accounts proceed in parallel; `test_locks_are_per_account` checks this.

## 2. Idempotency: `reference_id`

Clients retry when a network call times out, and they can't know whether the first attempt landed. `reference_id` is the client's key for "this exact operation".

| Situation | Response |
|---|---|
| New reference | Apply, **201** |
| Same reference, identical type, amount and description | **200** with the original transaction, header `Idempotent-Replayed: true`. Nothing is applied. |
| Same reference, different payload | **409**. This is almost certainly a client bug, and silently returning the old result would hide it. |
| Rejected debit (insufficient funds) | Nothing is stored, so the same reference can be retried after a top-up. |

A replay is checked **before** the balance. If a debit succeeded and the balance is now 0, a retry must still report the original success, not "insufficient funds". `test_retry_replays_even_if_balance_changed_since` covers this.

**Why not `account_id + transaction_id` as the reference?** `transaction_id` is generated by the server on every request, so a retry would get a new reference and post twice. That defeats the purpose. It would also duplicate two columns that are already indexed.

**Race safety.** The reference check runs under the account lock, so two simultaneous identical requests serialise: one inserts, the other sees it and replays. The `UNIQUE (account_id, reference_id)` constraint is a backstop that holds even if that logic were wrong.

## 3. Money

- Stored as `BIGINT` minor units. `0.1 + 0.2 != 0.3` in IEEE floats; `10 + 20 == 30` in integers. BIGINT holds about 9.2 × 10¹⁶ rupees.
- Parsed with `Decimal` at the edge, rejecting more than 2 decimal places instead of rounding. Silently rounding money is a bug.
- Returned as strings, so JavaScript clients don't lose precision on large values.

## 4. Business rules in Python, invariants in the database

`app/domain/rules.decide()` is a pure function of (balance, request, existing transaction). That makes every rule fast to unit-test (`tests/unit/test_rules.py`) and easy to read in a review.

The database independently enforces what must **never** be violated, whatever code runs against it:

- `CHECK (balance >= 0)`, `CHECK (amount > 0)`, `CHECK (balance_after >= 0)`
- `UNIQUE (account_id, reference_id)`
- A trigger that makes `transactions` append-only. Corrections are new entries, as in real accounting.
- Foreign key from transactions to accounts

`tests/integration/test_db_invariants.py` attacks these with raw SQL, bypassing the app.

*Earlier iteration:* the posting logic was a PL/pgSQL function. That was one round trip and also correct, but it hid the rules in SQL and made them harder to unit-test and review. I moved them to Python and kept the database as the safety net.

## 5. Stored balance plus `balance_after`

The balance is stored on the account, so reads are O(1). It is updated in the same transaction that inserts the ledger row. Each transaction also records `balance_after`, so the history is self-auditing: you can replay it and check every step. `test_balance_always_equals_sum_of_ledger` asserts that the stored balance equals the sum of entries.

## 6. API decisions

- **400 for malformed input, 422 for a valid request the business rules reject.** FastAPI uses 422 for validation by default. I split the two, so a client can tell "fix your request" from "the account can't afford this".
- **Unknown fields are rejected** (`extra="forbid"`). A client that sends `balance` learns immediately that it's ignored by design, instead of believing it worked.
- **Keyset pagination** on `(created_at, id)`. `OFFSET 100000` scans and discards 100k rows; a keyset seek is O(log n) at any depth. It's also stable when new rows arrive mid-scroll. Cursors are opaque, so the scheme can change later.
- **UUIDv7 ids.** Unguessable like v4, but time-ordered, so B-tree inserts append at the end of the index instead of splitting random pages.

## 7. Phone numbers as the customer identifier

- **Customers never see or type an internal ID.** They sign up and look up their account by mobile number. The API still returns the UUID, which clients use for later calls, but the UI never displays it.
- **Normalised to E.164 (`+91XXXXXXXXXX`) at the edge**, so `98765 43210`, `+91-98765-43210` and `098765 43210` are one account. The database enforces both the format (`CHECK`) and uniqueness (`UNIQUE`). A duplicate sign-up is caught by the constraint, not a read-then-insert check, so two simultaneous sign-ups can't both succeed.
- **Masked in every response** (`+91 ******3210`). The full number goes in and never comes back out.
- **Lookup is `POST /accounts/lookup` with the number in the body**, not `GET ?phone=`. Query strings end up in access logs, proxy caches and browser history.
- **This is identification, not authentication.** Anyone who knows a number can open that account. Production would verify it with an OTP and issue a short-lived session token, and every account route would check that token. The demo says clearly to use dummy numbers.
- **Migration `002_account_phone.sql`** adds the column as a separate, versioned change instead of editing `001`. That's how a schema evolves once it has shipped.

## 8. Operations

- `X-Request-ID` on every response, honoured if the caller sends one, and logged with method, path, status and latency as JSON.
- Database connectivity errors map to **503**, so clients know the request is safe to retry. Unexpected errors map to **500** with no internals leaked.
- Migrations are versioned, recorded in `schema_migrations`, and each runs in its own transaction.
- On Supabase, tables live in a private `ledger` schema with RLS on and no policies. The public anon and authenticated keys can't read or write money.

## 9. At a billion transactions

| Concern | Approach |
|---|---|
| Table and index size | Partition `transactions` by month on `created_at`. Every query filters by `account_id` and pages by time, so partition pruning works. Old partitions can move to cheaper storage. |
| Insert speed | UUIDv7 keeps index inserts sequential (already done). |
| History reads | The `(account_id, created_at desc, id desc)` index serves them; keyset pagination keeps deep pages cheap. |
| Hot accounts (thousands of writes per second on one account, e.g. a merchant) | The row lock becomes the bottleneck. Options: split the balance into N sub-balance rows and pick one at random for credits; or stop maintaining a live balance and append entries, deriving the balance from periodic snapshots plus recent entries. |
| Read load | Read replicas for history; balances stay on the primary for consistency. |
| Connection count | Transaction-mode pooling (PgBouncer/Supavisor). The code already disables server-side prepared statements for compatibility. |

## 10. Security hardening

A security review found the issues below. Each one is fixed and pinned by a test, so a regression fails the build.

| # | Weakness found | Fix | Where | Test |
|---|---|---|---|---|
| 3 | The app connected as the database owner. A bug or injected statement could disable the append-only trigger, drop tables or rewrite history. | Migration 003 creates a `ledger_app` role that can only `SELECT`/`INSERT` both tables and `UPDATE` the `balance` column, with RLS policies for that role alone. Every pooled connection runs `SET ROLE ledger_app` first. | `db/migrations/003_hardening.sql`, `app/db.py` | `test_least_privilege.py`: the app role can serve the API, but gets `InsufficientPrivilege` for update/delete/truncate/alter/drop/create |
| 4 | Text containing NUL or other control characters passed validation and was then refused by Postgres, so the client saw a **500**. | Names, descriptions and references reject control characters (Unicode `Cc`/`Cs`) and are NFC-normalised, so visually identical text is one idempotency key. Indic ZWJ/ZWNJ (`Cf`) stay allowed for correct Kannada spelling. Database "bad value" errors map to 400 as a safety net. | `app/domain/text.py`, `app/api/errors.py` | `test_hardening.py` |
| 5 | Python's `\d` matches any script's digits, so a full-width `９０００…` number passed the phone check and failed the database `CHECK` with a **500**. Also, `^…$` let a trailing newline through. | ASCII-only character classes and `fullmatch`. | `app/domain/phone.py` | `test_hardening.py` |
| 6 | No limit on request body size: the server buffered any size before validation. | ASGI middleware refuses an over-limit `Content-Length` before reading, and counts chunked bodies as they stream, cutting them off at the limit. | 7 | No database timeouts. One stuck transaction holding an account's row lock would block every request for that account until the pool gave up. | Each connection sets `lock_timeout = 3s`, `statement_timeout = 5s` and `idle_in_transaction_session_timeout = 10s`. A timed-out request rolls back and returns a retryable **503**. | `app/db.py`, `app/config.py` | `test_waiting_on_a_held_lock_times_out_with_503` |
| 8 | `X-Request-ID` was echoed into a response header and the logs exactly as received, at any length and with any characters. | Accepted only if it matches `[A-Za-z0-9._-]{1,64}`; otherwise a fresh ID is generated. | 9 | The append-only trigger is per row, and `TRUNCATE` fires no row triggers, so a truncate could wipe the ledger. | Statement-level `BEFORE TRUNCATE` triggers on both tables. They hold even for the owner, and the app role has no `TRUNCATE` privilege at all. | `db/migrations/003_hardening.sql` | `test_truncate_is_blocked_even_for_the_owner` |
| 10 | The Streamlit UI rendered the customer's name as Markdown, so a name could display as a link, heading, image or emoji. | User-supplied text is backslash-escaped before rendering. | `ui/markdown_safe.py` | `test_hardening.py` |

**Already safe, verified by the review:**
- **SQL injection:** every query is parameterised, and the only dynamic identifier (the schema name) goes through `psycopg.sql.Identifier`.
- **Mass assignment:** unknown fields are rejected.
- **Error responses:** 500s never include internals.
- **Supabase API roles:** they have no access to the ledger schema (`test_supabase_api_roles_have_no_access`).
- **Money:** amounts are exact integers, never floats.
- **Race conditions:** covered by the concurrency tests.

**What `SET ROLE` does and doesn't protect against:** it stops the application code, including any bug in it, from doing anything outside its grants. It isn't a wall against an attacker who can already run arbitrary SQL on the connection, because `RESET ROLE` undoes it. In production, give `ledger_app` `LOGIN` and its own password, and put that user in `DATABASE_URL`. The owner credentials are then used only by the migration job.

## 11. Known limitations

These were accepted as out of scope for this assignment:

- **No authentication or authorisation (review item 1).** Anyone who knows an account ID can post to it, and phone lookup returns that ID. In production every route would require a session token issued after OTP verification of the phone number, and would check that the token's account matches the path.
- **Phone numbers can be checked one by one (review item 2).** Lookup returns 200 or 404, and sign-up returns 409 for a taken number, with no rate limit. The fix is OTP-gated lookup, per-IP and per-number rate limits (e.g. at the API gateway), and one generic response whether or not the number exists.
- No account closure and no transfers. A transfer would lock both rows **in a fixed order (by id)** to avoid deadlocks, then post a debit and a credit atomically.
- Idempotency keys never expire. At scale they'd be kept for a retention window, e.g. 30 days, then archived.
- There is a per-transaction maximum but no daily limits or fraud rules.
